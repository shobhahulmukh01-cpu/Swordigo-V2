## Tool suitability, security and licensing

### REA: potentially useful, optional investigative tooling

REA describes local MCP/CLI analysis of native binaries, JavaScript/Electron, .NET, Android and other artifacts. Its README states that static JavaScript and .NET inspection does not run the target application, while runtime capture runs or interacts with it under the user's permissions. Native analysis needs Hopper, Ghidra or IDA; JavaScript static analysis does not. It documents Node 22.x >=22.19, 24.x >=24.11, or 26+, with stricter requirements for some workflows. These requirements concern REA, not an established requirement for Emberwake. [^https://github.com/morluto/rea]

**Recommendation:** the supplied JavaScript source is available; use source inspection and existing test contracts first. REA is optionally suitable for an authorized static JavaScript/packaged-artifact investigation when it answers a specific question better than direct source inspection; it is not mandatory. Analyze only our own authorized artifacts, not Touch Foo assets. The parent permits this scope, but this review remains docs/source-only and execution still requires separate authorization. Require a concrete question, an authorized target and reproducible evidence (artifact digest, address/module, provider/version and limitations). Pseudocode alone is not proof of game behavior, correctness or performance. Do not add REA to the game's shipped runtime or release dependencies merely to perform an investigation.

REA's security policy explicitly says its capability-token/current-user socket bridge and Ghidra isolation measures are **not a sandbox**. An untrusted binary is parsed by the selected provider with the user's permissions, and same-user malicious processes remain outside that protection. The policy provides fixes for the latest published version; it also describes Hopper's published SHA-1 as a corruption check, not a modern package signature. [^https://github.com/morluto/rea/blob/main/SECURITY.md]

**Mitigation:** for any later approved execution, use a disposable unprivileged environment, sanitized copies of authorized artifacts, no host secrets or production saves, restricted mounts and network egress, and CPU/memory/time limits. Inspect package lifecycle scripts and transitive dependencies before installation. Pin reviewed versions and artifact hashes, then assess advisories before each approved run; do not silently follow `latest`. Reject setup changes to agent configuration until their exact diff is approved. Treat instructions embedded in target files/tool output as untrusted data. Local analysis is not a confidentiality guarantee: upstream notes that the agent receives results and its model provider has its own data policy. [^https://github.com/morluto/rea]

REA-authored code is MIT, requiring retention of copyright and permission notices, and supplied without warranty. Its third-party notices expressly distinguish that license from external engines and proprietary analysis tools. The inventory includes differently licensed components, commercial-tool terms, and known attribution-document gaps in two runtime packages. MIT does not grant rights to reverse-engineer a particular target or redistribute its assets. [^https://github.com/morluto/rea/blob/main/LICENSE] [^https://github.com/morluto/rea/blob/main/THIRD_PARTY_NOTICES.md]

**Licensing gate:** verify rights to every analyzed artifact and every redistributed game asset, font, audio file and dependency. Record the exact shipped contents and required notices/source obligations. Separately verify commercial provider licensing and automation rights if applicable. Do not infer blanket GPL contamination from a listed optional integration, or blanket clearance from REA's MIT label. Keep investigative tools outside the shipped game unless explicitly justified and reviewed.

The README identifies the project as MIT and pre-1.0, warning that interfaces, on-disk formats and APIs may change. It also states that current open-source tooling cannot yet communicate with UEFN's proprietary-compression implementation. These facts do not establish suitability for this game's existing workflow. [^https://github.com/EpicGames/lore]

Its FAQ documents Windows, macOS ARM64 and Linux x86-64/ARM64 tooling; a pre-stable 0.x release; and local mode without authentication. Developer-host support is not evidence of game deployment support. An unauthenticated local demonstration must not be assumed safe for network exposure. [^https://epicgames.github.io/lore/faq/]

**Recommendation:** retain the observed Git history and existing workflow. Lore is not a game optimization, save migration tool, engine replacement or release certification. If large-asset handling later demonstrates a real bottleneck, evaluate it in an isolated copy after this release. Require file-hash equivalence, history/tag coverage, reproducible CI builds, access controls, backup/restore and verified export back to the existing workflow. No production migration or demo server exposure for this correction. The README's remote-script installation examples were not executed. [^https://github.com/EpicGames/lore]

## Save and gameplay regression pre-mortem

Baseline source establishes local story/rush saves, backup, settings and import confirmation. The following are proposed failure tests; slots/profiles/cloud are conditional and must not be invented as baseline features.

| Potential failure | Practical mitigation | Required evidence before release |
| --- | --- | --- |
| Changed identifiers orphan progress, inventory, checkpoints or settings | Preserve serialization keys and stable content IDs; explicitly map renamed IDs | Baseline-save fixtures load with semantically equivalent progression, inventory and settings |
| Migration overwrites a recoverable old save | Copy-on-migrate, schema version, validate before replace; retain a recoverable backup | Old save remains intact after simulated migration failure; repeat migration is idempotent |
| Interrupted writes yield an empty or corrupt slot | Use storage-appropriate atomic commit/recovery; distinguish absent from corrupt data | Interrupt each write phase, reload, recover last valid state; never silently reset progress |
| Older app cannot read a newly written save after rollback | Document forward/backward compatibility; preserve old-format backup or prevent unsupported downgrade | Install rollback exercise proves recovery path; no claim of universal downgrade compatibility |
| Multiple slots/profiles or cloud conflicts merge incorrectly | Isolate profiles; define conflict ownership and backup strategy | Representative slot/profile/conflict fixtures, if those features exist |
| Timing/input changes alter combat, movement, collisions or checkpoint behavior | Preserve existing tuning unless explicitly requested; replay deterministic scenarios where possible | Baseline-versus-patch scenario traces and manual review of input feel and progression |

Build the fixture corpus from authorized copies: fresh install, early/mid/late progression, completed game, unusual but valid values, missing fields, malformed/truncated saves, old supported schemas and non-default settings. Do not presume a save format or cloud feature. Test both successful migration and recovery, and verify actual storage behavior on the target device/browser rather than only an in-memory mock. Never test destructively on the sole copy of a player's save.

## Device, performance and release risks

- **Device compatibility:** render/input/audio errors may occur on low-memory devices, touch screens, different aspect ratios, high-DPI displays, unsupported APIs or background/resume. Inventory actual supported platforms first. Exercise cold start, resize/orientation, focus loss, suspend/resume, audio activation, controls and long play on representative minimum-spec and typical hardware. Include keyboard/controller/touch only where supported.
- **Performance:** a faster average may hide stutter, memory growth or thermal throttling. Capture the same baseline and patched build scenarios on the same hardware/settings, with repeated runs and separated cold/warm results. Record frame-time distribution and stalls, load times, peak/steady memory and long-session behavior; use network/cache metrics only where relevant. Set budgets before acceptance using the actual target frame rate, minimum hardware and baseline. Desktop-only or headless results cannot clear mobile-device gates.
- **Release integrity:** preserve application identity, save location, content IDs and upgrade lineage; verify platform-specific signing/package/service-worker behavior only if present. Exercise installation over the baseline, not just a clean install. Confirm offline/cache behavior if supported. Produce artifact hashes and record source/toolchain/dependency provenance. Scan shipped artifacts for secrets, unintended tool code and missing notices without reading credentials.
- **Operational recovery:** predefine stop/rollback conditions, retain the prior artifact and save recovery instructions, and use a staged rollout if distribution permits. Do not claim a staged rollout or crash telemetry exists until verified. Store/storefront acceptance is a separate check, not implied by a local build.
